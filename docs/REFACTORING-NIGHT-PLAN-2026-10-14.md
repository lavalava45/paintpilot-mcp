# PaintPilot — план ночного рефакторинга (14 октября 2026)

**Статус:** план, не отчёт о выполнении. **Режим:** небольшие проверяемые изменения без изменения поведения. **Приоритет:** не помешать текущей Beta-квалификации.

## Цель и границы

Снизить связанность кода в цепочке `Critic → Painter → Guard → Photoshop`, чтобы последующие исправления ошибок компиляции художественных проходов и восстановления сессий затрагивали меньше независимых политик. **Уменьшение размера файлов не является критерием успеха.** Рефакторинг сам по себе не улучшает реализм, композицию или качество рисования: ожидаемый выигрыш — предсказуемость, локальность изменений, диагностируемость и скорость разработки.

Документ подчиняется [AGENTS.md](../AGENTS.md), [архитектуре](architecture.md), [плану Release Hardening](RELEASE-HARDENING.md) и [roadmap](PAINTING-ROADMAP.md). Действует freeze необязательных функций. Если структурное изменение не помогает воспроизведённому дефекту либо требует существенного изменения поведения, **отложить его до завершения Beta-квалификации**. Ночь не является поводом расширять scope.

## Последовательность работ на ночь

### 0. Зафиксировать безопасную базу — обязательный входной gate

1. Прочитать актуальный `AGENTS.md` и owning-разделы документации; проверить `git status`, ветку, HEAD, текущие diff и наличие параллельных изменений.
2. Не делать `reset`, `checkout` поверх незавершённой работы, автоформатирование репозитория или массовое перемещение файлов. Наблюдавшееся 14.10 рабочее дерево содержит много незакоммиченных, включая новые файлы, изменений.
3. Определить для каждого выбранного файла точного владельца изменений и непересекающийся диапазон работы. При активных параллельных правках — **перейти в read-only** для пересекающихся участков.
4. Перед переносом логики записать нынешние экспортируемые API, формы ошибок, очередность независимых проверок и перечень уже существующих owning-тестов. Не принимать устаревшие числа тестов за результат нового прогона.

**Gate:** понятна исходная версия и гарантировано сохранение чужих изменений; иначе не редактировать код.

### 1. P0 — согласованное выделение 14 модулей ЗАВЕРШЕНО (source-only, техническая ветка)

Завершены 14 небольших срезов: 13 чистых выделений сохранены в коммите
`3151952`, а `compact-change-domains` с отдельно квалифицированным изменением
семантики Guard — в последующем коммите `c98fda1` ветки
`integration/night-refactor-20261014`. Проверены адресные тесты и полный
`verify:canonical` (PASS). Исходная ветка `digital-painting` **не продвинута**:
дальнейшая безопасная интеграция с её большим незакоммиченным деревом —
отдельная открытая задача. P0 закрыт только в согласованном объёме
source-level boundary helpers, а не как полное разбиение большой функции.

Ниже сохранены исходные условия и ограничения, актуальные для любого последующего переноса:

- Зафиксировать текущую последовательность: подготовка художественного метода/конструкции → валидации независимых полей → owner/layer/geometry/method checks → сбор итоговой операции.
- При новом, отдельно санкционированном этапе можно рассматривать **только ещё не выделенный** независимый набор чистых проверок/нормализаций с явным типизированным контекстом после чтения его зависимостей. Не возвращаться к уже выделенным semantic owner/layer, physical-stack, temporary-owner stage gate, compact envelope, budget, review-region, construction/material-role, brush material и change-domains без воспроизведённой ошибки. Особое внимание: cross-layer authority, geometry binding, negative-space/causal-effect revision binding и owner inheritance могут изменять поля или порядок отказов; без отдельного доказательства эквивалентности их не извлекать. **Дополнительных модулей в закрытый ограниченный P0 не входит.**
- Сохранить прежнюю структуру `GuardCycleCompileViolation`, пути полей, коды ошибок, порядок блокировок, одинаковое поведение при нескольких ошибках и pre-dispatch отказ.
- Не добавлять неявных художественных решений или эвристик по конкретным сценам/кистям. Не объединять взаимоисключающие проверки через общее `catch`, скрывающее точный код отказа.
- После каждого переноса запускать **адресные тесты** компилятора/контрактов; при регрессии либо устранить именно ошибку переноса, либо откатить только собственный срез.

**Gate:** те же входы дают эквивалентные нормализации, ошибки и операцию; не меняются Guard admission и объём обязательного review. Если для извлечения нужно изменить семантику — остановиться, оформить отдельную задачу Release Hardening с воспроизведением.

### 2. P1 — подготовить разбиение `SessionStore`; исполнение условное

Составить карту методов и их данных: хранение/atomic write и lock; identity/recovery/receipt; Critic/Director/priority; projection/metrics; owner/geometry bindings. Определить зависимости между группами.

Переносить только очевидно чистую расчётную группу **если** этап 1 стабилен, owning-тесты проходят и нет конфликта с параллельной работой. Публичные методы `SessionStore` пока оставить фасадом. **Не переносить этой ночью** `begin`, `complete`, `verdict`, `reconcile`, `closePreviousCycle`, `lock`, идентичность документа, журнал, барьеры и атомарные обновления состояния: риск невидимой смены recovery-семантики слишком велик.

**Gate:** прежние `record`/state/projection и recovery-инварианты; отсутствие побочных записей в выделенных чистых функциях. Если gate не выполняется — ограничиться картой модулей без изменений исходников.

## Инварианты (не ослаблять)

- Production dispatch — только UXP; все мутации через embedded Guard, raw mutation — `guard_required`.
- Fail-closed при неясной идентичности документа/слоя и при uncertain dispatch. Никакого автоматического replay; recovery только по durable evidence.
- Один ограниченный художественный проход, физическое владение независимыми семантическими частями, защита чужих слоёв и корректные History/rollback boundaries.
- Доставка и рассмотрение **точного** BEFORE/AFTER, Critic/global debt и current-frame authority; успешный код не заменяет художественное доказательство.
- Публичные MCP-схемы, коды ошибок, ответы, budget/latency и существующие запреты/авторизации остаются без семантических изменений.
- Не добавлять новую subsystem, host transport, fallback, фичи, telemetry-only тесты или специальные исключения для сцен.

## Критерий завершения ночного этапа

**Минимальный полезный результат:** безопасная базовая ревизия идентифицирована; хотя бы один небольшой независимый срез компилятора выделен и прошёл owning-тесты — **либо** документировано, почему работу пришлось остановить до изменений. Рефакторинг `SessionStore` считается отдельной условной задачей, не обязанностью любой ценой. Никаких заявлений об улучшении изображения или Beta readiness без отдельного Photoshop/evidence acceptance.
